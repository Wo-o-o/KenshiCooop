# Технический аудит KenshiCoop

Проверен checkout `Wo-o-o/KenshiCooop`, HEAD `5a761e19a4184b42315e96ea7e92e3c1403d54db`, протокол 55. Игровой код, штатные тесты и зависимости основного репозитория не изменялись. Все материалы аудита находятся вне checkout, в `/workspace/kenshi-audit`.

Это аудит реализации с локальными проверками доступных компонентов. Windows DLL и сценарии внутри Kenshi не запускались: текущая машина — Linux, а проект требует Visual C++ 2010 v100 x64, Windows SDK, Kenshi и RE_Kenshi. «Подтверждено» ниже означает подтверждённый путь в коде либо воспроизведение на извлечённой функции; это не заявление о воспроизведении симптома в живой игре.

## Как устроена синхронизация

- `NetLink.cpp`: ENet, UDP или Steam P2P; движение передаётся ненадёжными пакетами, события и инвентарь — надёжным каналом, сохранения/загрузка — отдельным bulk-каналом. Два игрока — штатная модель.
- `Inbound.h`: копии пакетов в очередях между сетевым и игровым потоками. Мутации движка выполняются в игровом потоке. Очереди состояния мира очищаются при смене сессии.
- `ReplicatorPublish/Authority/Drive/Spawn`: владение отрядами и ячейками, публикация персонажей, интерполяция, подавление локальной AI у копий, создание и сопоставление NPC, смена идентификатора при найме/переводе в отряд.
- `ReplicatorItems.cpp`: полные снимки контейнеров; отдельные каналы наземных предметов W1 и перемещения экипировки W2/W3; обмен между контейнерами определяется по изменениям количества. Временные поправки `xferLatch_` защищают локальный обмен от старых снимков.
- `EngineInventory.cpp`: чтение экипировки, свободных предметов и вложенных Inventory рюкзаков; сверка создаёт недостающие обычные предметы и уничтожает лишние. Создание рюкзаков при сверке запрещено для сохранения содержимого.
- `ReplicatorChannels.cpp`: здоровье, лечение, характеристики и общий денежный пул. `SaveXfer.cpp` и координатор в `Plugin.cpp`: сохранение хоста, ожидание завершения записи, передача файлов, промежуточный каталог, проверка хешей и замена каталога сохранения.

Есть полезные защитные механизмы: перенос реального объекта вместо пересоздания экипировки, пометка неполных снимков, защитные задержки при UI drag, проверки живости proxy, защита собственных персонажей от входящей сверки, перенос death/KO latch при смене hand. Главные риски находятся на границах этих механизмов.

## Обнаруженные проблемы

P1 — потеря/дублирование состояния или нарушение целостности; P2 — устойчивое несовпадение свойств, отложенная сходимость либо менее частые условия. Уверенность относится к механизму, а не к частоте в игре.

### A01. Пустой рюкзак не очищается на другой стороне — P1

**Файл/функция:** [EngineInventory.cpp:934](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:934), `applyContainerContents`; выход на строке 958 и `if (nk == 0) continue` на строке 984.

**Причина:** вложенная Inventory сверяется только при наличии дочерних строк. Снимок рюкзака, из которого забрали последний предмет, содержит сам рюкзак и ноль детей. Такой снимок никогда не сверяет его содержимое с пустым списком. При нескольких контейнерах пустой контейнер также пропускается, даже если другой содержит детей.

**Последствие:** на копии рюкзака остаются предметы, которые владелец уже перенёс, использовал или продал. Перенос последнего предмета в другой контейнер может оставить дополнительную доступную копию.

**Уверенность:** высокая; вызов оригинальной `applyContainerContents` с имитацией API подтвердил: верхний уровень обработан, вложенный — ни разу. Исправлять после A02: отсутствие детей можно считать пустотой только в полном снимке.

### A02. Лимит снимка достигается без `TRUNCATED` — P1

**Файл/функция:** [EngineInventory.cpp:249](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:249), `readInvItems`; также условие цикла секций на строке 257.

**Причина:** циклы родителей и секций останавливаются по `n < maxOut`. Если верхний уровень заполнил буфер ровно или последняя вмещённая строка завершила секцию, код не заходит в следующий участок, где выставляется `trunc=true`. Неучтённые дочерние предметы могут существовать, но снимок объявляется полным.

**Последствие:** частичный список детей сверяется с разрешением удаления и уничтожает оставшиеся предметы на копии. При полностью пропущенных детях действует A01: вместо удаления сохраняется старое содержимое. Эти два исхода зависят от места достижения лимита.

**Уверенность:** высокая; оба граничных случая воспроизведены на оригинальной `readInvItems` с имитацией объектов. Тестовый буфер уменьшен для компактности; те же условия применяются к штатному лимиту 64.

### A03. Поправка после обмена ломает ссылки на родителя — P1

**Файл/функция:** [ReplicatorItems.cpp:283](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:283), `applyInventories`.

**Причина:** при отрицательном latch строки с нулевым количеством удаляются через `adj.erase`, но `parentIdx` у остальных строк остаётся прежним. На wire это индекс родителя в исходном массиве плюс один.

**Пример:** `[еда, рюкзак, ребёнок(parentIdx=2)]`; после удаления еды получается `[рюкзак, ребёнок(parentIdx=2)]`. Правильная ссылка уже должна быть 1. Ребёнок оказывается сиротой или связывается с другим предметом. Кроме того, подсчёт `want` включает вложенные строки, а локальное чтение для сравнения latch — только верхний уровень.

**Последствие:** пропуски применения содержимого рюкзака, неправильная привязка, неверное завершение защиты обмена.

**Уверенность:** высокая для сдвига индексов; реальное проявление зависит от одновременного обмена и вложенного снимка. Требуется отображение старых индексов в новые и явная обработка удаления родителя.

### A04. Каналы состояния обходят сопоставление локальных персонажей — P1

**Файлы/функции:** [ReplicatorDrive.cpp:160](/workspace/KenshiCooop/src/plugin/sync/ReplicatorDrive.cpp:160), `applyTargets`; [ReplicatorChannels.cpp:226](/workspace/KenshiCooop/src/plugin/sync/ReplicatorChannels.cpp:226), `applyMedical`, `applyStats`, `applyTreatments`; [Replicator.h:2145](/workspace/KenshiCooop/src/plugin/sync/Replicator.h:2145), `handForContainerKey`; `applyInventories`.

**Причина:** движение при невозможности разрешить удалённый hand использует `proxyByKey_`. Здоровье и характеристики вызывают напрямую `engine::resolveCharByHand`; инвентарь разрешает hand напрямую, переводя только fixtures. `insertPeerMember` явно фиксирует, что локальный hand после найма/смены отряда обычно отличается от удалённого.

**Последствие:** персонаж может корректно двигаться как proxy/rekeyed body, но не получать здоровье, характеристики, инвентарь и операции над предметами. Это особенно относится к runtime NPC и новым рекрутам; совпадающие hand персонажей из общего сохранения обходят проблему.

**Уверенность:** высокая для непоследовательности разрешения; сценарий найма с различными hand требует Windows-проверки. Исправление должно использовать существующее сопоставление с проверкой живости, сохранив проверки authority, а не менять модель владения.

### A05. Неудавшийся DROP считается окончательно обработанным — P1

**Файл/функция:** [ReplicatorItems.cpp:1045](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:1045), `applyWeaponDrops`; аналогичный ранний dedup в `applyTransfers`.

**Причина:** `(ownerId, dropId)` заносится в `appliedDrops_` до разрешения контейнера и перемещения. Если контейнер не загружен, отказ остаётся без очереди повторения. ENet подтверждает доставку пакета, а не успешную операцию движка. Комментарий о повторе отправителем не реализован здесь: DROP ставится в очередь один раз, и повтор идентичного id всё равно пропускается.

**Последствие:** рюкзак остаётся в старом месте на копии либо позже уничтожается снимком удаления, пока на стороне владельца лежит на земле. Его восстановление через фабрикацию запрещено. Одноразовый отказ обмена также может закрепить расхождение.

**Уверенность:** высокая. Нужны состояния «ожидает применения / успешно применено / окончательно отклонено» и ограниченный повтор после разрешения объекта.

### A06. Поиск источника обмена пропускает вложенные предметы и допускает фабрикацию при отказе — P1

**Файлы/функции:** [ReplicatorItems.cpp:1564](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:1564), `detectAndPublishTransfers`, `xferRebase`, `applyTransfers`; [EngineInventory.cpp:1277](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:1277), `moveItemBetweenContainers`.

**Причина:** детектор и перемещение читают верхний уровень без `includeNested`. У `moveItemBetweenContainers` нет аналога поиска в рюкзаке, который уже есть в `relocateWeaponToGround`. Результат 0 объединяет отсутствие предмета, неразрешённый hand и отказ назначения. `applyTransfers` компенсирует любой недобор созданием предметов, если тип допускает фабрикацию.

**Последствие:** предмет из рюкзака не участвует в корреляции обмена. Если реальная копия находится вне прочитанной части либо назначение отказало и предмет вернулся в источник, попытка создать недобор может нарушить сохранение количества. Локальные переносы между верхним уровнем и рюкзаком могут быть ошибочно сочтены потерей, а затем DROP fallback.

**Уверенность:** высокая для неполного поиска и объединения причин; вероятность фактического дублирования при отказе зависит от `tryAddItem`. Заголовки KenshiLib подтверждают, что операции возвращают успех/отказ, но реализации движка в репозитории нет. Нужны полные чтения и раздельные результаты перед разрешением фабрикации.

### A07. ACK обмена освобождает защиту до получения актуального снимка — P1

**Файлы/функции:** [ReplicatorItems.cpp:1829](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:1829), `applyXferAcks`; `publishInventories`, `applyInventories`; `NetLink::run` и вызовы в `Plugin.cpp`.

**Причина:** любой ACK снимает вклад latch целиком. Он подтверждает перемещение на получателе, но не получение инициатором снимка, учитывающего перемещение. Снимки проходят settle 350/1800 мс; сетевой цикл отправляет queued inventory перед ACK. На игровом потоке ACK применяется перед сверкой.

**Последствие:** старый снимок может восстановить уже забранный предмет или удалить отданный. Окончательная сходимость после следующего снимка не исключает промежуточную доступную копию. При partial/reject восстановление только peer-конца не гарантирует согласованного обратного перемещения собственного конца.

**Уверенность:** высокая для окна гонки, средняя для устойчивого дублирования после дальнейших действий игрока. Нужен причинный признак актуальности снимка; одного ACK и сравнения суммарного количества недостаточно.

### A08. Свойства предмета учитываются в хеше, но не исправляются при равном количестве — P2

**Файл/функция:** [EngineInventory.cpp:593](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:593), `applyToInventory`; `ContentHash.h::invEntryHash`.

**Причина:** группы сверки объединяются по `(stringID,itemType)` и количеству worn/loose. Качество и grade используются при создании недобора, но при одинаковом количестве уже существующие предметы не обновляются. Разные grade одного template сводятся к последнему grade группы; manufacturer/material берутся из первого непустого значения.

**Последствие:** снимки продолжают приходить с различающимися хешами, а предметы остаются разного качества/производителя. Например, у автора Masterwork, на копии Shoddy при одинаковом количестве. Ошибочная корреляция одинаковых template также может переносить другую копию.

**Уверенность:** высокая; оригинальная `applyToInventory` на имитации Inventory не выполнила ни одной мутации при изменённом grade/quality и различающемся хеше. Нужна сверка мультимножества свойств без безусловного уничтожения реальных вещей.

### A09. Подбор наземных обычных предметов не оставляет отметку о потреблённом netId — P1

**Файлы/функции:** [ReplicatorItems.cpp:583](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:583), блок CLAIM в `publishWorldItems`; `applyWorldItems`, `applyWorldClaims`.

**Причина:** при локальном подборе proxy удаляется из `worldProxies_`, отправляется CLAIM. Уже отправленный до обработки CLAIM снимок того же `(owner,netId)` снова считается новым и создаёт proxy. Отметки «этот netId уже потреблён» нет. При отказе удаления оригинала `applyWorldClaims` удаляет track и прекращает попытки, оставляя реальный предмет без учёта.

**Последствие:** повторное появление доступного предмета до cull; если его успевают подобрать, cull уже не находит его mapping. Это особенно опасно при большом RTT и повторной публикации.

**Уверенность:** высокая для последовательности состояний, средняя для окна повторного подбора в игре. Нужен tombstone потреблённого id на время сессии и повтор отказавшей операции.

### A10. У наземного proxy не применяются количество и качество обновлений — P2

**Файлы/функции:** [ReplicatorItems.cpp:621](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:621), `applyWorldItems`; [EngineInventory.cpp:1609](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:1609), `spawnWorldItemProxy`.

**Причина:** существующему proxy обновляется только позиция. Новый получает quantity, но функция создания вообще не принимает quality из `WorldItemEntry`. Хеш автора включает quantity/quality, поэтому новые снимки публикуются, но не меняют эти свойства копии.

**Последствие:** расходящиеся размеры наземных стеков и состояние предметов; последующий подбор переносит неверное количество.

**Уверенность:** высокая по интерфейсу и веткам. Нужно безопасно применять свойства к живому proxy, с учётом уже потреблённого id из A09.

### A11. «Не удалось прочитать» смешивается с «пусто»; применение не повторяется — P1

**Файлы/функции:** [EngineInventory.cpp:569](/workspace/KenshiCooop/src/plugin/game/EngineInventory.cpp:569), `captureContainerContents`; [ReplicatorItems.cpp:18](/workspace/KenshiCooop/src/plugin/sync/ReplicatorItems.cpp:18), `publishInventories`, `applyInventories`.

**Причина:** отсутствие Inventory возвращает `n=0`, hash=0, truncated=false. Публикатор проверяет существование RootObject, но не успешность чтения Inventory. Достаточно длительный отказ выглядит как устойчивый пустой контейнер. При приёме `dirty=false` ставится до вызова движка; неразрешённый объект или неуспешная операция не возвращают снимок в ожидание.

**Последствие:** потенциальное удаление предметов по ложному пустому снимку; при отказе применения — задержка до safety resend 5/30 секунд. Логи `APPLY` отражают вызов, а не доказанное совпадение.

**Уверенность:** высокая для неоднозначного интерфейса; средняя для частоты ложного пустого чтения в живой игре. Возвращать отдельно статус чтения, completeness и статус сходимости; повторять только безопасные операции.

### A12. Ограждение состояния после загрузки неполное — P1

**Файлы/функции:** [NetLink.cpp:303](/workspace/KenshiCooop/src/plugin/net/NetLink.cpp:303), `bumpSessionEpoch`, `acceptEpoch`, отправка entity на строке 1857; `Plugin.cpp::sessionResetForWorldReload`, `Inbound::flushWorldState`.

**Причина:** epoch есть у движения, но отсутствует у inventory/drop/xfer/medical и других world-пакетов. Reset очищает inbound и `out_` движения, оставляя остальные исходящие очереди; уже летящие старые reliable пакеты могут попасть в очищенный мир. Даже motion-снимок и epoch не копируются атомарно: сетевой поток может скопировать старые `ents`, затем главный поток увеличить epoch, и старые сущности уйдут с новой epoch.

**Последствие:** применение старого инвентаря/здоровья/предметных операций после загрузки, повторное создание предметов, воздействие на объект с совпадающим hand. Bulk LOAD_GO не устанавливает порядок относительно другого канала.

**Уверенность:** высокая для неполноты fencing, средняя для конкретного runtime-проявления. Сначала атомарно связать motion capture и его epoch; затем оградить world-state сообщения при reload, сохраняя сообщения самого координатора загрузки.

### A13. Проверка сохранения не доказывает правильность итоговых файлов — P1

**Файл/функции:** [SaveXfer.cpp:590](/workspace/KenshiCooop/src/plugin/sync/SaveXfer.cpp:590), `onSaveFile`, `onSaveDone`, `folderFingerprint`.

**Причина:** накопительный FNV считается по поступившим chunk bytes, без проверки ожидаемого offset и привязки fileIdx к одному path. Результат `SetFilePointer` не проверяется. `onSaveDone` сравнивает эти накопительные значения и seen, а не содержимое staging на диске; не сверяет итоговый размер. В `folderFingerprint` ошибка `ReadFile` не отличена от штатного EOF.

**Воспроизведение:** передать `ab` по offset 0, затем `cd` опять по offset 0; CRC передать для `abcd`. Приёмник считает 4 байта, успешно делает commit, но файл содержит только `cd`. Оригинальные тела функций вызваны с имитацией Win32 файлового API.

**Уверенность:** высокая. Штатный sender использует правильные последовательные offsets; это подтверждённый дефект валидации, а не доказательство повреждения от обычной потери UDP. ENet надёжность этот дефект не исправляет. Нужны контроль path/offset/размера, обработка ошибок IO и проверка финального staged состояния перед swap.

### A14. Имя сохранения не ограничено одним каталогом — P1

**Файл/функции:** [SaveXfer.cpp:559](/workspace/KenshiCooop/src/plugin/sync/SaveXfer.cpp:559), `onSaveBegin`, `saveFolderFor`, `onSaveDone`; `relPathSafe`.

**Причина:** имя из `SaveBeginPacket` прямо участвует в пути, последующей очистке `__incoming`/`__old` и замене каталога. `relPathSafe` проверяет только относительный путь chunk, а не имя сохранения; также не запрещает NUL внутри заявленной строки path. Пакетное имя может содержать переходы между каталогами.

**Последствие:** некорректный или специально сформированный пакет хоста может записывать/удалять данные за пределами назначенного save-каталога. Это риск доверительной границы сохранений; штатное имя из игрового меню обычно безопасно.

**Уверенность:** высокая по построению путей. Проверять имя как единственный безопасный компонент и итоговое расположение каталога до любых файловых мутаций; rejecting не должен затрагивать существующий save.

### A15. Раздельные очереди сохранений меняют порядок между transfer — P2

**Файлы/функции:** [Plugin.cpp:352](/workspace/KenshiCooop/src/plugin/Plugin.cpp:352), `pumpSaveReceive`; `Inbound::pushSaveBegin/File/Done`; `SaveXfer::onSaveBegin`.

**Причина:** pump сначала обрабатывает все BEGIN, затем все FILE, затем все DONE. Последовательность wire `BEGIN A, FILE A, DONE A, BEGIN B` в одном игровом drain превращается в `BEGIN A, BEGIN B, FILE A, DONE A`. Старый transfer теряет активное состояние прежде, чем его завершение обработано. BEGIN/FILE/DONE извлекаются также не одним общим атомарным drain.

**Последствие:** завершённое сохранение A может не быть записано, особенно если A/B — разные slots. Продолжительный следующий transfer или его отказ увеличивает эффект. При одном последовательном transfer механизм работает; при явной отмене старой передачи потеря старого результата может быть ожидаемой.

**Уверенность:** высокая для изменения порядка, средняя для влияния на штатный поток сохранений. Сохранить общий порядок событий bulk или явно завершать/отменять transfer с проверяемым результатом. `abortAll` также не сбрасывает receiver и его открытый handle; отключение до DONE оставляет receiving активным до нового BEGIN.

## Дополнительные риски, требующие targeted проверок

1. `EngineInventory.cpp::moveItemBetweenContainers`: результат возврата предмета в источник при отказе назначения не проверяется. `removeByKey` игнорирует bool от `removeItemAutoDestroy` и считает предмет удалённым даже при отказе. Уверенность в отсутствии проверки высокая; фактическая потеря требует проверки поведения движка.
2. `readInvItems`: дедупликация primary/secondary оружия по template может объединять две реальные одинаковые копии. Комментарий объясняет, что engine exposes alias objects; менять на pointer-only dedup без Windows-пробы опасно. Уверенность средняя.
3. `applyContainerContents`: одинаковые рюкзаки сопоставляются по локальному порядку, не по устойчивой общей идентичности. Общее содержимое может совпасть, а содержимое конкретных копий — поменяться. Штатный движок ограничивает несколько рюкзаков на одном персонаже, поэтому это требует подходящего контейнера/fixture. Уверенность средняя.
4. `retryPendingPickups`/`reconcileGroundGear`: после таймаута остаются явно признанные duplicate-risk состояния; site fallback выбирает template+близость, а не качество и экземпляр. Не уничтожать такую копию без доказательства существования нужного предмета в назначении. Уверенность высокая в оставшемся риске, частота неизвестна.
5. `NetLink::run`: host допускает восемь ENet peers; ветка `id >= 2` только пишет ошибку и продолжает WELCOME. `nextId` растёт при reconnect, поэтому сам id не доказывает третьего игрока. Штатную двухпользовательскую модель следует обеспечивать числом активных peers.
6. Парсер доверяет packet ownerId, многим enum/parentIdx и NUL-терминации фиксированных строк. `strcmp`/`std::string` в downstream предполагают валидные строки; ограничения sender не заменяют проверки receiver. Добавить проверку допустимого отправителя/направления, количества inventory <= 64, parent references и строк до использования. Это дефекты robustness против некорректных пакетов; отдельный аудит безопасности может расширить перечень.
7. Общий кошелёк допускает одновременные траты двумя сторонами, затем ограничивает отрицательный итог нулём (`applyMoneyPool`, OVERDRAFT). Уже полученные товары не откатываются. Это экономическое нарушение сохранения стоимости, отличное от дублирования одного объекта. Исправление требует решения о поведении одновременной покупки и поэтому не предлагается первым.

## План исправлений

1. **Сначала A02:** достоверная пометка неполноты вложенного снимка. Сохранить fail-safe поведение, запрещающее удаления по неполной информации. Затем A01: корректная сверка пустого вложенного контейнера только по полному снимку. Проверки: полный buffer на границе верхнего уровня, секции и родителя; заполненный → пустой рюкзак; два контейнера, один пустой; truncated desired/local; общий подсчёт предметов до/после.
2. **A03, A05, A06, A11:** сохранить parent indices после поправок, различать отсутствие и отказ, безопасно повторять deferred операции, учитывать вложенные источники. Не фабриковать на основании недостоверного чтения. Проверки: drop рюкзака во время unload, отказ dst, предмет внутри bag, больше 64 строк, повтор id, source/destination quantity conservation.
3. **A07 и A09:** причинно безопасное завершение обмена и учёт consumed world ids. Проверки с задержкой/loss: stale snapshot перед ACK, partial/reject, повторный snapshot после pickup, отказ CLAIM deletion, два последовательных обмена одного template.
4. **A04 и A12:** единое использование существующей hand/proxy translation для всех каналов и защита от старого мира. Проверки: runtime NPC/recruit с различными hand, смерть+rekey, reconnect, reload при queued inventory/drop/medical, переключение эпохи между capture и send. Не переносить raw pointers через reset.
5. **A13–A15:** безопасный save commit и жизненный цикл transfer. Проверки: offset overlap/gap, duplicate path, IO fail, missing files, unsafe name, A→B в одном drain, disconnect до DONE, rollback при невозможности rename. Отказ проверки должен сохранять предыдущий loadable save.
6. **A08/A10 и дополнительные риски:** точность grade/manufacturer/quality/quantity, bool результатов движка, границы двух игроков и валидность пакетов. Тесты одинаковых template разного grade и нескольких экземпляров проводить с реальными engine objects.

Каждый шаг — отдельное небольшое изменение с negative regression. Для предметных исправлений acceptance criterion: совпадает не только hash, но и мультимножество предметов по владельцу/контейнеру/свойствам; количество и вложенное содержимое сохраняются через move/drop/pickup/trade/save/reload. Не заменять игровой инвентарь, не ограничивать стандартные действия Kenshi и не отключать прямой обмен как постоянное решение.

## Первое небольшое исправление — предложение, не применено

**A02 в `readInvItems`:** убрать `n < maxOut` из внешних циклов родителей и секций вложенного capture. После заполнения output продолжать ограниченный осмотр оставшихся секций уже захваченных родителей. Существующая внутренняя проверка `if (n >= maxOut) { trunc = true; break; }` сможет обнаружить действительно пропущенный qualifying item до записи в буфер.

Объём изменения — два условия циклов плюс регрессионные проверки. Wire layout, лимит 64, модель владения и правила игры сохраняются. Полный, ровно заполненный снимок без дополнительных предметов не должен ошибочно помечаться truncated; реально пропущенный предмет должен выставлять флаг. Это безопасный первый шаг перед исправлением A01, которое разрешит очистку пустого рюкзака и поэтому обязано опираться на достоверную completeness.

Предложенные два изменения проверены **только в отдельной копии функции вне checkout**: оба случая пропущенных детей стали возвращать `truncated=true`, а ровно заполненный список без пропусков сохранил `truncated=false`. [Лог проверки предложения](/workspace/kenshi-audit/inventory-proposal-check.log). Основной игровой код не изменён. Этот опыт не заменяет проверку v100 и реального движка.

Необходимая Windows-валидация после реализации: v100 prototest, `inv_nested_bag` с переходом к нулю и capture boundary cases, `trade_peer`, gear drop/pickup, сохранение и перезагрузка двухклиентной сессии. Архитектурная переработка для этого первого шага не нужна.
